# Carzen · Supabase

Database, auth and storage for the Carzen platform, kept as code. Supabase is the
**infrastructure behind the Carzen API**, not a replacement for it: the apps keep calling
`/api/v1` (contracts in `packages/contracts`), and only the API layer talks to Supabase with
the service role key. When the business outgrows this, a Laravel API can implement the same
contract on the **same Postgres database**; the switch is `NEXT_PUBLIC_API_URL`.

> Status (2026-10-15): schema, security, storage, auth config and demo seed are ready and
> validated. The API still uses the in-memory mock; wiring `packages/platform-api` to this
> database is the next phase.

## Schema at a glance (40 tables)

Full reference (every column, constraint and index, in Arabic): `docs/carzen-database-schema.html`.

- **Platform:** `areas`, `service_categories`, `amenities`, `platform_settings`, `admin_users`, `admin_role_permissions`
- **Washes:** `businesses`, `business_settings`, `branches`, `branch_working_hours`, `branch_amenities`, `branch_blocked_slots`, `branch_photos`, `services`, `staff`, `staff_shift_patterns`, `staff_shifts`
- **Customers:** `customers`, `vehicles`, `customer_favorites`
- **Orders & money:** `orders`, `order_items`, `order_events`, `order_notes`, `payments`, `transactions`, `payouts`, `day_closings`
- **Engagement:** `reviews`, `offers`, `offer_branches`, `offer_categories`, `complaints`, `complaint_notes`, `wash_applications`
- **Activity:** `admin_notifications`, `vendor_notifications`, `customer_notifications`, `push_devices`, `audit_logs`

Conventions: snake_case, prefixed text ids (`ord_…`, `br_…`, matching the API), bilingual
text as jsonb `{ar, en}`, money `numeric(10,2)` EGP, `timestamptz`, phones in E.164
(`+20…`), `created_at` / `updated_at` with triggers. All are Laravel-compatible.

What the database guarantees on its own:
- **Integrity:** enums, foreign keys, and checks. Examples:
  - `total = subtotal − discount`;
  - a cancelled order has a reason;
  - a cash difference needs a reason;
  - an offer percent is ≤ 50;
  - an approved application has a business.
- **Atomic numbering:**
  - `next_order_number('app' | 'walk_in' | 'phone')` returns `CZ-10001…`, `CZ-20045…` and `CZ-30023…` with no duplicates under concurrency;
  - `next_complaint_ticket()` returns `TK-1040…`.
- **Ratings:** branch and business ratings follow the visible reviews automatically (a trigger).
- **The audit log is append-only:** `UPDATE` and `DELETE` are rejected.
- **A day is closed once per branch.**

Business rules (pricing, the order state machine, owner and manager permissions) stay in the
API layer, by design.

## Security model

- RLS is **enabled on every table with no policies**. All privileges are revoked from `anon` and `authenticated`. Default privileges keep future tables the same.
- Only the server-side API uses the **service role** (it bypasses RLS). The publishable/anon key alone can read nothing.
- If a client later needs direct access (e.g. Realtime for the live board), add a narrow policy in a new migration. Never disable RLS.
- Storage:
  - `application-documents` is private (PDF/JPG/PNG, 10 MB, signed URLs only).
  - `branch-photos` is public (JPG/PNG/WebP, 5 MB).
  - There are no object policies: uploads go through the API.
- Auth:
  - Email sign-up is closed (admins are invited).
  - Phone OTP sign-up is open for customers.
  - Minimum password length is 8.
  - The OTP resend interval is 60 s.

## Apply to a Supabase project

Prerequisites: Node 22+ and access to the Supabase organisation. The CLI runs through `npx`.

1. **Create the project** in the dashboard.
   - Region: `eu-central-1` (Frankfurt), the closest available region to Cairo.
   - Plan: Free is fine for trials, but free projects pause after a week idle. Use **Pro** for anything people rely on.
2. **Link and push the schema** (from the repo root):
   ```bash
   npx supabase login
   npx supabase link --project-ref <project-ref>
   npx supabase db push --include-seed    # or: npm run db:push:seed
   ```
   Use `npx supabase db push` (`npm run db:push`) for later migrations, without re-seeding.
3. **Create the demo accounts.**
   - Copy `supabase/.env.example` to `supabase/.env`.
   - Fill `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` (Dashboard → Project Settings → API).
   - Then run:
   ```bash
   npm run db:users:demo
   ```
   This creates the following accounts and links each one to its profile through `user_id`:
   - **Admins:** email + `demo1234` (e.g. `sara@carzen.demo`).
   - **Staff:** phone + `demo1234` (owner `+201200000000`, manager `+201005550102`).
   - **Customers:** phone only.
4. **Auth settings on the hosted project.** Either apply `config.toml`'s auth section with `npx supabase config push`, or set the same values in the dashboard:
   - email sign-up off, phone sign-up on;
   - site URL and redirect URLs set to the real domains (not localhost) in production.
5. **SMS for phone OTP:** Authentication → Providers → Phone.
   - Twilio Verify is the only provider that can also send the code over WhatsApp. Check Egyptian sender-ID rules.
   - Add the demo numbers as *Test phone numbers* with OTP `123456`.
6. **Generate database types** for the API layer:
   ```bash
   npx supabase gen types --lang typescript --linked > packages/platform-api/src/supabase/database.types.ts
   ```
7. **Check the advisors:** Dashboard → Advisors (security + performance).
   - Expected: an *INFO* "RLS enabled, no policy" notice on each table. It is intentional (see the security model above).

## Day-to-day

- **Schema change:** `npx supabase migration new <name>`, write the SQL, then run `npx supabase db push`. Never edit a migration that was already pushed.
- **Demo data:**
  - Run `npm run db:seed:generate` after changing `packages/platform-api/src/seed.ts`, and commit `seed.sql`.
  - The seed ends with a block that moves all dates by whole days to the day it is applied, so the demo always looks current.
- **Re-seed a remote project:** `npx supabase db reset --linked`. ⚠️ This **deletes all data** in that project. Never run it on production.

## Notes for the Claude session that applies this

- Read this file, then run steps 2–7 with the user's own credentials.
- Never commit `supabase/.env`, the service role key or database passwords. Never paste them into app code.
- Do not disable RLS or add broad policies. Do not edit pushed migrations; add new ones.
- After pushing, verify with: `select count(*) from orders;` → 1078, and `select public.next_order_number('walk_in');` → `CZ-20045`.
  - That second query consumes a number. Run it on a fresh seed only, or ignore the gap.
