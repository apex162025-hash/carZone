كل الجداول عليها RLS بدون أي policy، والصلاحيات مسحوبة من anon وauthenticated. يعني لو التطبيق استخدم supabase_flutter بالـ anon key وعمل select على أي جدول، هيرجع permission denied. ده مقصود ومش عطل.

الآن

اللوحتين يوصلوا للبيانات من طبقة API على السيرفر بمفتاح service_role. منطق البزنس (التسعير، حالات الطلب، صلاحيات المالك والمدير) في الطبقة دي.

المرحلة 2 (المقترحة)

Supabase يبقى الباك إند الكامل للكل:

  • القراءة: policies ضيقة لكل دور. العميل يشوف بياناته بس، والموظف يشوف فرعه بس.
  • الكتابة: دوال (RPC) فيها قواعد البزنس والتحقق من الصلاحيات. التطبيقات الأربعة تستخدم نفس الدوال، ومفيش كتابة مباشرة في الجداول.

الأمان والتخزين والدخول

الحماية مفروضة من القاعدة نفسها

الصلاحيات
  • RLS مفعّل على كل الجداول الـ 40، من غير policies حاليًا.
  • كل الصلاحيات مسحوبة من anon وauthenticated على الجداول والـ sequences والدوال، وأي جدول جديد بعد كده بنفس القاعدة.
  • service_role للسيرفر فقط. ممنوع يتحط في التطبيق أبدًا.
التخزين (Storage)
  • application-documents: خاص. للمستندات (PDF/JPG/PNG)، حد أقصى 10 ميجا، والوصول بروابط مؤقتة.
  • branch-photos: عام. لصور الفروع (JPG/PNG/WebP)، حد أقصى 5 ميجا.
تسجيل الدخول (Auth)
  • العملاء: بالموبايل + كود OTP، والتسجيل مفتوح.
  • فريق المغسلة: بالموبايل + كلمة سر. الحسابات بيعملها المالك.
  • فريق كارزن: بالإيميل + كلمة سر، والتسجيل الذاتي مقفول.
  • كلمة السر 8 حروف على الأقل، وإعادة إرسال الكود كل 60 ثانية، ونص الرسالة: «رمز الدخول إلى كارزن».
الرسائل (SMS)

Supabase بيدعم Twilio وVonage وMessageBird. Twilio Verify هو الوحيد اللي يبعت الكود على واتساب كمان. لازم تراجعوا تسجيل اسم المرسل في مصر.

دليل الدمج

تطبيق القاعدة دي على مشروع Supabase بتاعك

قبل أي خطوة
  • خُد نسخة احتياطية من المشروع (Dashboard → Database → Backups، أو npx supabase db dump).
  • جرّب الأول على مشروع تجريبي أو Branch، مش على المشروع اللي عليه مستخدمين.
  • متعدّلش أي migration من الـ 8 بعد ما تتطبق. أي تغيير يبقى migration جديدة.

  1. اربط المشروع ووثّق اللي عندك

    من فولدر المشروع اللي فيه supabase/:

    npx supabase login
npx supabase link --project-ref tbcmgdwzarfdgzzmmele
npx supabase db dump --schema-only -f current-schema.sql   # ابعتهولنا

  2. حدّد حالتك

    الحالة أ: المشروع فاضي أو فيه تجارب بس

    لا توجد بيانات مهمة. امسح جداول التجارب (أو ابدأ مشروع جديد)، وطبّق القاعدة مباشرة (الخطوة 4).

    الحالة ب: فيه جداول عليها بيانات تهمك

    نعمل خريطة بين جداولك وجداولنا وننقل البيانات (الخطوة 3). هنا مكان جدول واحد لكل مفهوم: ممنوع يفضل جدولين لنفس الشيء (مثلًا bookings وorders).

  3. الحالة ب: خريطة الدمج ونقل البيانات

    اربط كل جدول عندك بالجدول المقابل هنا. الأسماء الشائعة:

    عندك غالبًاالمقابل هناملاحظة
    profiles / userscustomers · staff · admin_usersملف لكل نوع، وكلهم بـ user_id → auth.users
    carsvehiclesاللوحة الموحّدة تتحسب لوحدها
    bookings / reservationsorders + order_items + order_eventsالبنود والمسار الزمني في جداول منفصلة
    washes / centers / shopsbusinesses + branchesالشركة ممكن يكون لها أكتر من فرع
    services / packagesservicesلكل فرع، type = primary أو addon
    ratingsreviewsتقييم واحد لكل طلب
    notificationscustomer_notifications · vendor_notificationsصندوق لكل طرف
    favoritescustomer_favorites
    device_tokens / fcm_tokenspush_devices

    طريقة النقل الآمنة:

    -- 1) غيّر اسم جدولك القديم عشان مايتعارضش (ولو فيه enum بنفس الاسم غيّره كمان)
alter table public.bookings rename to legacy_bookings;

-- 2) طبّق الـ migrations (الخطوة 4)، وبعدين انقل البيانات. مثال لعميل:
insert into public.customers (id, user_id, name, phone, created_at)
select 'cu_' || replace(p.id::text, '-', ''),   -- UUID القديم يتحفظ كنص ببادئة
       p.id,                                     -- لو profiles.id هو نفسه auth.users.id
       p.full_name, p.phone, p.created_at
  from public.legacy_profiles p;

-- 3) قارن الأعداد، وبعد ما تتأكد احذف القديم
select (select count(*) from public.legacy_profiles) as old, (select count(*) from public.customers) as new;
drop table public.legacy_profiles;

    التليفونات لازم تبقى E.164 (+20…) عشان القيد. لو عندك صيغ تانية، وحّدها في الـ select.

  4. طبّق الـ migrations وبيانات العرض

    npx supabase db push --dry-run          # يعرض اللي هيتطبق من غير ما يطبقه
npx supabase db push --include-seed     # الجداول + بيانات العرض (لمشروع تجريبي)
npx supabase db push                    # الجداول بس (لمشروع عليه بيانات حقيقية)

    لو المشروع اتعمل من الـ Dashboard من غير migrations، وdb push طلب history: نفّذ npx supabase db pull الأول. ده بيسجّل الحالة الحالية كـ migration أساس، وبعدها ادفع.

  5. الحسابات والإعدادات

    cp supabase/.env.example supabase/.env   # حط SUPABASE_URL و SUPABASE_SERVICE_ROLE_KEY
